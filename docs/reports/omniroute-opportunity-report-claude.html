1. Executive summary

OmniRoute is a mature, professionally engineered AI model gateway/router (TypeScript/Next.js, MIT licence, npm package omniroute@3.8.51). It solves "send this chat-completion request through the cheapest/most-available of 356 providers, with quota-aware fallback and up to ~89% token compression." It does not solve the problem ai-dev-orchestrator exists for: driving a multi-step software-delivery lifecycle (WorkItem → adaptive worker/profile selection → TDD execution via Ralph → quality gate → independent review → durable cross-worker/cold-restart handoff → release → realization/activity reporting → roadmap synthesis/approval) with governance guarantees (no silent quality downgrade, author≠reviewer, fail-closed everywhere, full audit trail).

OmniRoute operates one layer below where our orchestrator operates: it is a thing Claude Code/Codex CLIs can be pointed at as their model backend, or a launcher (omniroute run claude). It has no WorkItem, MVP, quality gate, independent-review policy, or durable crash-resumable handoff. Its "cloud agent" integration (Jules/Devin/Codex Cloud/Cursor Cloud) and "issue agent" are thin, single-shot delegations to external agents — not a replacement for our WorkItem state machine.

Where OmniRoute is genuinely stronger: breadth of provider/model coverage and free-tier aggregation; a more mature token-level quota/routing engine (fair-share, burn-rate, subscription-vs-metered billing classification, reset-aware ladders); request-level prompt compression; and test/CI maturity (mutation testing, nightly resilience/security suites, CodeQL, Semgrep).

This is not a close call. OmniRoute and ai-dev-orchestrator answer different questions. Neither Ralph nor our orchestrator is threatened by OmniRoute's existence; if anything, OmniRoute is a candidate provider underneath our stack, never a candidate replacement of any orchestration layer.

4. Current architecture (ai-dev-orchestrator)

Project (workspace, roadmap, current MVP)
  -> MVPManager (WorkItems, dependencies, durable handoff)
  -> WorkerSelector (capability > governance > quota > cost; adaptive tier since Slice 17)
  -> RalphExecutionEngine (real `ralph` subprocess: hats, TDD, review)
  -> ExecutionRecord + HandoffRecord (audit + durable resume)
  -> ValidationStore / QualityGateRunner (real commands, fail-closed)
  -> ReviewStore (independent review, author != reviewer enforced)
  -> ReleaseManager -> ActivityReport (MVP/release-level)
  -> PlanningCoordinator -> RoadmapProposal -> ApprovalCoordinator -> RoadmapApplicationService
  -> RealizationReport (WorkItem-level, deterministic, non-LLM aggregation)

Underneath WorkerSelector: ProviderAdapter.probe() (ClaudeCodeAdapter, CodexAdapter — read-only CLI-quota probes) → QuotaManager (freshness/TTL cache over multi-window ProviderState, e.g. Claude's 5h/7d windows). This is a CLI-subscription quota model, not an API-key/token-billing model.

12,069 lines of Python across src/orchestrator/, 25 modules, ~29 test files, 766 tests passing at last count. Real, versioned proof of a genuine cross-worker (Claude Code → Codex), cold-restart-safe handoff exists: docs/reports/real-cross-worker-resume-2026-09-13.html.

5. OmniRoute architecture

Any OpenAI/Anthropic-compatible client (Claude Code, Codex, Cursor, Cline,
  raw HTTP, LangChain/CrewAI/AutoGen via A2A, MCP clients)
    -> POST /v1/chat/completions (or /v1/responses, A2A JSON-RPC, MCP tool call)
    -> OmniRoute Smart Router
         - capability/combo selection (356 providers / 1312+ model ids)
         - RTK + "Caveman" prompt compression (documented 15-95%, ~89% avg)
         - 19 routing strategies (auto/cheapest, auto/quality,
           auto/subscription, auto/thrifty, ...)
         - allocation -> quota telemetry (healthy/approaching_limit/
           exhausted/unavailable/unknown) -> circuit breaker
           (closed/open/half_open) -> provider dispatch
    -> one of 356 upstream providers

Separately: omniroute run <cli> launches a supported coding CLI as a child process with its model backend redirected — a convenience launcher, not a task/workflow orchestrator. cloudAgent/ is a thin registry+adapter (jules, devin, codex-cloud, cursor-cloud) submitting a single CloudAgentTask (status: queued/running/awaiting_approval/completed/failed/cancelled) to an external hosted agent — no WorkItem dependency graph, no quality gate, no independent-review policy. issueAgent/ triages a GitHub issue via one chat-completion call.

Node/TypeScript, Next.js app router, ~82 top-level src/lib/* modules, 5000+ test files, nightly mutation/resilience/security CI suites.

6. Ralph architecture (recap)

Ralph Orchestrator (Rust, MIT, ~158k LOC — studied previously in docs/ECOSYSTEM.md/docs/SPIKE_RALPH.md): hats/roles with per-hat backend/model config, event bus, completion promises, git auto-commit, worktrees + parallel loops/waves, a review preset. No QuotaManager for CLI subscription windows, no cost/governance-ranked WorkerSelector, no structural (only configurable) author≠reviewer guarantee — exactly the gap ai-dev-orchestrator closes. OmniRoute does not change this: it has no hats/event-bus/TDD-loop concept at all — not a Ralph competitor, a different kind of system entirely.

8. OmniRoute vs our orchestrator

Different problem classes. Ours answers "did this WorkItem get built correctly, safely, and auditably, across possibly-crashing processes and possibly-different workers?" OmniRoute answers "which of 356 providers should serve this one HTTP chat-completion request, at what cost, with how much of the prompt trimmed?" No meaningful overlap at the orchestration level. The only genuine overlap is quota-awareness as a concept — but the unit of governance differs: ours governs which worker (CLI identity) may run a WorkItem; OmniRoute governs which provider connection may serve a request.

9. OmniRoute vs Ralph

No meaningful overlap. Ralph is an execution-loop engine; OmniRoute is a request router. omniroute run claude merely launches Claude Code with its model backend redirected — Ralph is not involved and is not replaced.

10. OmniRoute vs both combined

Even summing Ralph's and our orchestrator's capabilities, OmniRoute does not cover the union: no WorkItem/MVP concept, no quality gate, no independent review, no durable cold-restart handoff, no release/roadmap governance, no TDD execution loop. It adds things neither of us has (356-provider routing, compression, free-tier aggregation, MCP/A2A surfaces) but nothing that substitutes for either's core responsibilities.

11. Functional overlap

  1. Quota-awareness — moderate overlap, different unit of governance (see §19).
  2. Provider abstraction — weak overlap; different scale and purpose (2 CLI probes vs 356 request-serving connections).
  3. CLI launching — superficially similar, but OmniRoute's launch has no ExecutionRecord, no quality tier, no verdict parsing, no audit trail; it is a convenience wrapper, not an execution engine.

Everything else (WorkItem lifecycle, review, quality gates, handoff, reporting, roadmap/approval) has zero overlap.

12. Components to KEEP (as-is)

All WorkItem-lifecycle and governance components: ProjectStateStore, MVPManager, HandoffStore/HandoffRecord, WaitCoordinator, RecoveryCoordinator, QualityGateRunner/ValidationStore, ReviewStore, ReleaseManager/ActivityReport, PlanningCoordinator/RoadmapProposal, ApprovalCoordinator, RoadmapApplicationService, RealizationReport/Service/Store, ExecutionStore/ExecutionRecord, WorkerSelector, WorkerRegistry, ExecutionProfile/QualityTier, ComplexityEstimation*, AdaptiveExecutionSelector/ Decision/DecisionStore, RalphExecutionEngine/ExecutionRequest.

13. Components to EXTEND

None required by OmniRoute today. One optional, low-priority future idea: an additional, clearly-labeled OmniRouteRoutingAdapter used only if a Worker's backend is ever a raw HTTP-API call (not a CLI subprocess) — additive, never replacing the existing CLI-subscription probes for alice/victor.

14. Components to REPLACE

None. No component in src/orchestrator/ has an OmniRoute equivalent that is both functionally comparable and semantically compatible with our governance model.

15. Components to REMOVE

None. Nothing in our stack becomes redundant by OmniRoute's existence.

16. New capabilities worth knowing about (not adopting now)

  • Free-tier aggregation/catalog — useful only for a future non-CLI-subscription worker.
  • Prompt compression (RTK + "Caveman") — potentially interesting for token-cost reduction on a future API-key worker; figures not independently verified this session, so treated as MARKETING_ONLY until measured; not applicable to our current CLI-subprocess workers.
  • Subscription-vs-metered billing classification — conceptually validates our own principle, not directly reusable (governs request dispatch, not worker selection).
  • MCP server — could matter later for exposing our own orchestrator to other agents; unrelated to today's need.
  • Circuit breaker pattern — clean design, INSPIRE-only; our retry/recovery needs are already narrower and handled elsewhere.

17. Routing analysis

Three candidates considered:

  • A — CURRENT (recommended): WorkerSelector/AdaptiveExecutionSelector remain sole routing authority; OmniRoute, if ever used, sits strictly below a Worker's backend call.
  • B — OmniRoute controls routing (rejected): would usurp WorkerSelector's job; OmniRoute has no WorkItem/quality-tier/ author≠reviewer concept and its "subscription" rung governs OAuth chat connections, not our CLI worker identities.
  • C — constrained hybrid (possible future POC only): WorkerSelector keeps full authority; only a chosen Worker's own backend implementation could, if ever changed to an HTTP-API call, use an OmniRoute endpoint as transport — with auto/* disabled/pinned to prevent silent model substitution.

18. Quality-tier / no-downgrade guarantee feasibility

Verdict: NO. OmniRoute's auto/* routing optimizes for cost/latency/quota across interchangeable candidates — it has no notion of "this WorkItem requires at least COMPLEX and must never silently receive SIMPLE," and no equivalent of our NoCapableProfileError fail-closed filter. If ever used underneath a Worker (Candidate C), the model id would have to be pinned explicitly, never delegated to OmniRoute's own scoring, to preserve the guarantee.

19. Quota strategy

Decision: KEEP our QuotaManager/ ProviderAdapter design unchanged — not REPLACE, not naively AGGREGATE. Our model must never conflate Claude Code subscription quota, Codex subscription quota, Anthropic API budget, OpenAI API budget, third-party budgets, or local-model budgets. OmniRoute's quota engine (fair-share, burn-rate, plan registry, connection recovery) is a per-request/per-connection billing ledger for providers it proxies — a different governance unit than our per-CLI-subscription-window probes. Feeding alice/victor through it would add indirection with no governance benefit.

20. Resilience

Confirmed: OmniRoute delivers infra-level resilience (circuit breakers, classified transient-vs-permanent failures, bounded probe/cooldown re-entry). Our orchestrator delivers business-level recovery (RecoveryCoordinator distinguishing "still RUNNING after a crash" from "INTERRUPTED but WorkItem never transitioned out"; WaitCoordinator translating diagnosed quota exhaustion into scheduled resume). Complementary in principle, not substitutable.

21. Context / handoff

No — NOT_FOUND equivalent to our durable cold-restart handoff. OmniRoute's src/lib/memory/* is RAG-style conversational memory for chat continuity, not a structured, insert-only, WorkItem-scoped fact record proven to survive a genuinely separate OS process picking up work (as our real smoke test demonstrates for alice→victor). OmniRoute's A2A task manager is a JSON-RPC lifecycle for routing requests through OmniRoute as an agent skill provider, not a durable handoff mechanism for a third-party WorkItem — confirming the warning "A2A != durable handoff." Decision: KEEP HandoffStore/HandoffRecord unchanged.

22. Reports / audit

Decision: KEEP. No OmniRoute feature resembles our RealizationReport (deterministic, non-LLM, insert-only, per-WorkItem aggregation). OmniRoute's dashboards are operational telemetry for the router itself — a different audience and fact kind. REPLACE/EXTEND/MERGE are inapplicable — nothing to replace/extend/merge with.

23. Cost / token optimization opportunities

  • Prompt compression — MEDIUM_TERM (documented and coded, but figures unverified this session; not usable while workers run as full CLI subprocesses).
  • Free-tier aggregation — LOW_VALUE today, MEDIUM_TERM if a non-CLI worker is added.
  • Subscription-vs-metered ladder — AVOID for our current architecture (re-modeling CLI workers as OmniRoute "connections" adds complexity with no governance benefit).
  • Adopting OmniRoute wholesale for cost reasons — AVOID (no measured cost problem justifies the migration risk).

24. Security

LOW risk if ever adopted narrowly (Candidate C); MEDIUM if exposed as a shared network service. OmniRoute has its own auth/authz/CORS/origin layers, a SECURITY.md, a docs/security/ directory (WAF, ban detection, CLI token handling, compliance, egress policy, error sanitization, and MITM/TLS- stealth documentation — the last being a provider-terms-of-service evasion feature worth flagging as an operational/legal risk category, not a vulnerability in OmniRoute itself). CI includes CodeQL, Semgrep, a security scorecard, gitleaks, nightly LLM-security tests. Mitigation if ever adopted: run network-isolated, minimal credentials, never let auto/* routing touch a governed WorkItem execution path.

25. Maintainability

OmniRoute: very actively maintained, large contributor base, heavy CI, but a very large fast-moving surface (82 src/lib/* modules, 132KB README, 2.6MB CHANGELOG) — a real burden risk if depended upon: breaking changes, provider deprecations, and a Node/TS/Next.js/Docker/ Electron stack foreign to our Python/sqlite3/stdlib-only codebase (12,069 lines, 25 modules, 766 tests, deliberately small and auditable).

26. Operations (Linux target)

OmniRoute runs as a persistent network service (Docker/fly.toml/nix), with a documented memory-sizing gotcha for coding-agent-sized contexts — meaningfully different from our fully-local, no-daemon, subprocess-per-execution model. Adopting it, even narrowly, adds an always-on service to operate/monitor/patch.

31. Migration plan

Not applicable — no migration is recommended. If the optional S2 addition is ever pursued: (1) confirm a genuine non-CLI, API-key-based worker need exists; (2) build an isolated OmniRouteRoutingAdapter implementing the existing ProviderAdapter interface, pinned to an explicit non-auto model id; (3) add it to config/workers.yaml as a new profile, never replacing existing CLI-subscription profiles; (4) run the existing offline suite plus a new adapter-specific suite; (5) one cost-bounded real smoke test before trusting it in the loop. Pure addition — no existing component modified.

32. Rollback plan

Not applicable — no change is made this session. If the optional S2 addition is ever implemented: remove the adapter/profile from config/workers.yaml and delete the adapter module; purely additive, so no data migration or backfill is needed to roll back.

33. Risks

  • Status quo: no new risk identified beyond already-tracked remaining roadmap work (Slice 19/20).
  • Narrow S2 adoption (not done now): adds an always-on external dependency for a currently-hypothetical benefit.
  • Broad adoption (S3–S7): total loss of this project's functional purpose; not recommended.
  • This audit's own limits: read broadly (README, key docs, module structure, representative source, quota/routing/resilience/security subsystems, test/CI config) but did not execute OmniRoute's test suite or benchmark its compression claims — flagged explicitly rather than asserted as fact.

34. POC needed (proposed, NOT executed this session)

No POC is required to support the primary decision — the functional-coverage gap is not close. A POC would only matter if the optional S2 addition is ever seriously considered:

  1. Add a throwaway omniroute worker profile pointed at a local OmniRoute instance, pinned to one explicit non-auto model id.
  2. Run one disposable WorkItem through the real RalphExecutionEngine with this worker as developer.
  3. Verify: ExecutionRecord/quality gate still work unchanged; OmniRoute's own quota/circuit-breaker state never overrides WorkerSelector's decision; killing the OmniRoute process mid-execution produces the same RECOVERY_REQUIRED handling as any other backend failure.
  4. Explicitly do not wire auto/* routing into this POC — pin the model id.
